**Date:** 16 October 2026

## Assessment

The application has progressed: the API menu is integrated, the ordering layout is coherent at the intended portrait size, the standard simulated checkout works, and several earlier cart/session defects are fixed. It is **not ready for unattended production use**. Payment recovery still has correctness gaps, checkout retries bypass validation, and the API integration exposes empty and inconsistent customer screens.

| Area | Assessment | Main reason |
|---|---|---|
| Consistency | Needs correction | Venue identity changes between screens; product translations are incomplete; current-price validation still uses a different data source by default. |
| Speed | Acceptable in the measured desktop samples; resilience insufficient | Attract-screen DOM mounted in 0.40–2.12 s with warm cache. API latency dominated. Startup has no application timeout and blocks transaction recovery. |
| UI/UX | Normal ordering works; exception flows need substantial work | Clear cart totals, quantity controls and table-number entry, but an empty home page, inaccessible recovery entry and missing dialog focus management. |
| Production readiness | Do not approve yet | The P1 findings below and unverified real payment/POS/failover integration remain release blockers. |

This is an application/code audit with targeted browser and regression checks. It is not a penetration test, formal accessibility certification, exhaustive model checking, or evidence of real-infrastructure failover.

## Prioritized findings

P1 means a release blocker for unattended real ordering. P2 means a concrete functional or usability defect that should be corrected before rollout. Findings are separated from infrastructure that has not yet been integrated.

### F01 · P1 — Unknown payment recovery can submit an unconfirmed order

**Source:** [controller.ts:435](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/payment/controller.ts#L435), [controller.ts:493](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/payment/controller.ts#L493).

After restarting a persisted `starting` payment whose provider lookup returns `unknown`, the controller enters `assistance`. `submitRetry()` nevertheless permits `submitOrder()` from that state. The submission guard only requires identifiers and a snapshot; it does not require confirmed payment and sends an empty transaction reference when none exists.

**Evidence:** Audit test A01 restores this exact scenario and records **one POS submission instead of zero**. This is a controller defect even though the customer UI currently also has a separate recovery-access problem. A real backend's possible rejection is not a substitute for the client guard.

**Required change:** Track confirmed payment explicitly and allow order submission only with verified approval/recoverable paid state. Keep unknown outcomes locked for reconciliation.

**Acceptance:** Unknown/corrupt/starting recovery records cannot submit or start a new charge; verified approved records can resubmit with the same idempotency key.

### F02 · P1 — Payment retry bypasses price, availability and authority checks

**Source:** [Pay.tsx:164](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/ui/Pay.tsx#L164), [checkout.ts:126](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/app/checkout.ts#L126).

The declined, terminal-offline and cancelled buttons call `startPay()` directly. That function only checks controller retry eligibility and a nonempty cart; it bypasses `toPay()` and its availability/price validation. A guest retry can therefore charge an obsolete amount or proceed with unavailable products, even after authority has changed.

**Evidence:** A04 clicks the actual rendered declined-state retry button. Availability is **never checked** before the controller's next start is requested.

**Required change:** Route every new charge attempt through one shared preflight, including any required price-change confirmation. Keep “resubmit an already paid order” separate from “charge again.”

**Acceptance:** A price/stock/authority change between decline and retry blocks or reconfirms appropriately; uncertain outcomes never allow a second charge.

### F03 · P1 — Authority is checked before asynchronous preflight, but not afterward

**Source:** [checkout.ts:51](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/app/checkout.ts#L51), [checkout.ts:95](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/app/checkout.ts#L95).

`toPay()` checks the connection before awaiting catalog/availability work. After those awaits it checks the cart signature but not the current writable authority. `priceConfirm()` also proceeds to `startPay()` without a fresh authority check.

**Evidence:** A03 changes the connection from connected to `no-authority` while availability is pending. The payment controller is still asked to start once the response resolves.

**Required change:** Revalidate the current session/cart and writable authority immediately before the charge boundary. The real adapter/backend must also enforce authority fencing; a UI check alone cannot eliminate every race.

**Acceptance:** Losing or changing authority during preflight or the price-confirmation dialog causes no new payment attempt until the new authority is resolved and validated.

### F04 · P1 — The assistance screen provides no usable staff recovery entry

**Source:** [Pay.tsx:133](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/ui/Pay.tsx#L133), [App.tsx:163](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/app/App.tsx#L163).

The pure `assistance` panel renders no action buttons. The application's staff gesture is attached to logo images in the attract screen/brand lockup, neither of which is present in the payment panel. The message tells the guest to obtain assistance but provides no on-screen route for staff to open the existing tools.

**Evidence:** A02 renders a corrupt-record assistance state and finds **zero buttons**. The containing App's staff-tap selector confirms the missing entry route.

**Required change:** Provide a persistent authenticated staff entry on all payment and recovery states, display available order/attempt identifiers, and retain the protected transaction while staff investigate.

**Acceptance:** Staff can reach diagnostics and reconcile a corrupt or unknown recovery state using the kiosk UI, without reloading, deleting storage or unlocking a new guest order prematurely.

### F05 · P1 — An unbounded menu request can prevent payment recovery from running

**Source:** [catalogSource.ts:44](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/adapters/http/catalogSource.ts#L44), [App.tsx:34](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/app/App.tsx#L34), [data.ts:33](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/engine/data.ts#L33).

Boot waits for the entire brand pack and then the remote menu before creating/restoring the payment controller. The menu fetch has no application-level timeout or abort. A hanging menu service can leave the device on “Starting…” and prevent recovery of a previously persisted transaction, even if the payment adapter is available. A menu error likewise diverts to boot failure before transaction recovery.

**Evidence:** Confirmed by the startup dependency order and fetch implementation. The network timing samples verify that menu retrieval sits on the startup critical path; a real outage was not injected into the provider.

**Required change:** Bound catalog requests, separate transaction recovery from optional menu rendering, and provide a recovery UI that does not require the catalog to load. Define a safe cached-menu policy without allowing stale prices to bypass authoritative checkout validation.

**Acceptance:** With a persisted transaction and a hanging/failing menu endpoint, the device still performs payment reconciliation and exposes staff recovery within a defined timeout.

### F06 · P2 — Selected API upsell products escape stock validation

**Source:** [draft.ts:280](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/engine/draft.ts#L280).

API upsell items carry a `ModItem.pid`, but `includedPids()` collects only the main product, legacy menu side/drink and cross-sells. Selected API step items in `draft.extras` are omitted. Consequently, their stock status is not considered when validating the configured product.

**Evidence:** A05 selects a valid API upsell item, marks its product ID unavailable, and still receives **zero validation issues**.

**Required change:** Include selected step/extra product IDs in availability and disabled-product validation; identify the unavailable option in the product and cart UI.

**Acceptance:** An unavailable required option blocks checkout and directs the guest to replace it; unavailable optional items can be removed explicitly.

### F07 · P2 — A late loyalty response can attach the previous guest to a new order

**Source:** [Overlays.tsx:48](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/ui/Overlays.tsx#L48).

`VoucherSheet.submit()` awaits identification and then mutates the global member state without checking whether the dialog or guest session still exists. Closing/resetting the order while the request is pending does not invalidate the response. There is also no rejected-request feedback or in-flight submission guard.

**Evidence:** A07 starts identification, resets the guest session, resolves the old response, and finds `previous-guest` attached to the new session.

**Required change:** Bind asynchronous loyalty operations to a session generation, discard stale results, and handle pending/error/timeout states.

**Acceptance:** Closing/resetting during identification never changes a later guest's membership or credits their purchase to the earlier account.

### F08 · P2 — The default API home page has no products

**Source:** [Shell.tsx:235](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/ui/Shell.tsx#L235), [tmkMapper.ts:234](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/adapters/http/tmkMapper.ts#L234), [tmkMapper.ts:278](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/adapters/http/tmkMapper.ts#L278).

`HomeMain` expects promotions and `pop`/`new` product badges. The API mapper intentionally clears promotions and does not populate those merchandising badges. Starting an order therefore opens “UITGELICHT / POPULAIR / NIEUW” with empty sections and “Bekijk alles” links. The category sidebar works, but the main entry surface appears unfinished.

**Evidence:** Reproduced with the default live API menu in the production build at 1080×1920.

**Required change:** Provide a category/product fallback when merchandising data is absent, or start at the first available category. Hide empty sections and links that lead to empty lists. Do not invent popular-product rankings.

**Acceptance:** Every supported API menu opens on a useful screen with an obvious product-selection path, including menus with no promotions or badges.

### F09 · P2 — Product names do not switch to the selected API language

**Source:** [tmkMapper.ts:244](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/adapters/http/tmkMapper.ts#L244), [engine/types.ts:25](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/engine/types.ts#L25).

Categories and descriptions are mapped as localized values, but product `name` is permanently copied from the primary API tree into a plain string. Changing the language updates surrounding UI while retaining the original product names, even when translated API names exist.

**Evidence:** A06 supplies distinct Dutch and English names in the existing bilingual API fixture, switches to English, and still gets the Dutch name.

**Required change:** Preserve translated product names and resolve them consistently in cards, detail screens, cart and customer-facing summaries, with a defined fallback.

**Acceptance:** A bilingual fixture with deliberately different names displays the selected translation throughout the ordering journey.

### F10 · P2 — Venue identity changes between welcome and ordering screens

**Source:** [Attract.tsx:37](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/ui/Attract.tsx#L37), [Shell.tsx:77](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/ui/Shell.tsx#L77).

The welcome screen uses the API venue name/logo, whereas the sidebar uses `E().brand` from the DADAWAN fixture. The audited default menu showed **Tapas Mainstreet** on welcome and **DADAWAN / ASIAN KITCHEN** once ordering began. The page title and marketing copy also remain tied to the fixture brand.

**Required change:** Resolve venue branding once and use it throughout the interface, including title, sidebar, welcome and relevant receipts. Use neutral fallback copy when venue-specific content is absent.

**Acceptance:** Testing two different venues produces a consistent identity across every screen, without fixture-brand leakage.

### F11 · P2 — Current price-variant updates are ignored

**Source:** [checkout.ts:29](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/app/checkout.ts#L29).

`catalogRefresh()` applies `cur.prices` but ignores `cur.variants`. The retained static/brand-pack engine still uses those variants for premium menu drinks and cross-sells. A changed variant therefore does not trigger price confirmation. This affects the retained static/adapter path; API mapping currently empties price variants.

**Evidence:** A08 changes the `lychee-menu-upgrade` variant through `catalog.current()` and detects **no price changes** for the existing configured meal.

**Required change:** Apply and version all supported pricing inputs before revalidation, including variant prices. Preserve immutable snapshots for started/paid orders.

**Acceptance:** Changing a selected variant triggers an exact old/new price confirmation before a new charge; paid snapshots remain unchanged.

### F12 · P2 — Modal dialogs do not contain keyboard focus

**Source:** [Overlays.tsx:27](https://github.com/Slobodan-Krdzev/kiosk_claude/blob/85a3ff728db5445413c4183b700fbff661eb2fdb/kiosk-web/src/ui/Overlays.tsx#L27).

`aria-modal` is declared, but the shared sheet/dialog primitives do not move focus, trap it or make the background inert. In the browser, opening the allergen filter left focus on its background trigger; pressing Tab focused the background language button rather than the dialog.

**Required change:** Move focus inside the dialog, contain navigation, disable background interaction, support appropriate dismissal and restore focus to the trigger. Ensure every dialog and input has an accessible name.

**Acceptance:** Tab/Shift+Tab remain within the active dialog; background controls cannot be activated; closing restores focus. Verify with keyboard and the target device's assistive technology.

## Speed findings and next measurements

| Measurement | Result |
|---|---:|
| Main JavaScript | 421.19 kB, approximately 124.93 kB gzip |
| CSS | 103.49 kB, approximately 21.95 kB gzip |
| Brand-pack JSON requests before API request | 23 per boot |
| Attract DOM mounted, three samples | 2.116 s / 0.444 s / 0.402 s |
| Remote menu request, corresponding samples | 1.925 s / 0.334 s / 0.194 s |
| First contentful paint | 0.168 s / 0.120 s / 0.196 s; this can be the startup screen, not the loaded menu |
| Observed startup long tasks | None in these three samples |

Method: production bundle served by local Vite preview, warmed browser cache, no network/CPU throttling, lightweight PerformanceObserver instrumentation in a copy of `dist/index.html`. “Attract DOM mounted” means the welcome component appeared; it does not mean every remote image had decoded. Cross-origin transfer sizes were not exposed. Raw summarized measurements and the probe are in the evidence folder. These are small-sample diagnostic measurements, not p95, Lighthouse scores or a cold-start benchmark.

The priority is startup robustness and unnecessary dependencies, not speculative micro-optimization. Split essential branding/translations from demo catalog fixtures; avoid waiting for all 23 fixture files before starting the API request; add bounded requests and an explicit recovery state. Then measure cold starts and image decoding on the actual kiosk. Image loading is already lazy/asynchronous in relevant components, and money calculations use integer cents; retain these strengths.

The normal cart flow provides useful feedback: product counts and totals are clear, adding an item updates the order bar, the table-number screen enforces a range, and the simulated success screen distinguishes payment, order acceptance and printing. Preserve this clarity when fixing error paths.
