# Backend dependencies (kiosk)

Capabilities the kiosk needs from the Guestit backend that do not exist yet or need a decision from the backend
owner (CLAUDE.md rule 3). The client side is implemented behind the adapter interface; the affected behaviour is
classified honestly, never rounded up.

| # | Capability | What exists today | Requirement | Client status | Classification |
|---|---|---|---|---|---|
| B1 | **Live prices / price validation** | None. Prices come from the startup menu (`getfullresources`). The old kiosk sends the unit prices it computed in `POST CreateKioskOrderWithPinPayment` and performs no check (`docs/reference/kiosk-product-checks.md`, "Prices"). | Either (a) the backend validates the order's unit prices against the current menu and rejects a mismatch with a distinguishable response, or (b) a cheap "current prices / menu version" call the kiosk can run before charging. Confirm (a) or provide (b). | `CatalogAdapter.current()` on the API returns no changes and stamps the menu load time as the catalog version (`src/adapters/http/tmkLive.ts`). The price-change dialog therefore never fires on API menus. | `BLOCKED_BACKEND` |
| B2 | **Batch availability** | `GET checkProductAvailable?idProduct=<id>`: one product per request, bare boolean. | Optional: one request for several ids. Not blocking — the kiosk checks one product on tap and only the cart's products before charging (bounded to 4 in flight). | `src/adapters/http/tmkLive.ts` fans out per product. | `IMPLEMENTED` (client) |
| B3 | **Out-of-stock test data** | The dev menu (2408) has no out-of-stock product; `checkProductAvailable` returned `true` for every id tried, HTTP 500 for an unknown id. | A product on the dev menu that answers `false`, so the sold-out path can be verified live. | Sold-out handling is covered by tests on a mocked adapter only. | `NOT_VERIFIED_ON_REAL_INFRA` |
| B4 | **Order submission idempotency** | `POST CreateKioskOrderWithPinPayment` is one blocking call that starts the PIN payment and prints; the old kiosk sent `OrderGuid: ""` and re-sent the whole order with `skip=true` after a "Printing problem" (`docs/reference/kiosk-payment-flow.md`, issue 3). | The backend de-duplicates on `Order.OrderGuid` (same guid → same order and no second charge). The kiosk now sends its stable order id there. Needed for the one resend path: "Printing problem" without an order number. | `src/adapters/http/tmkOrder.ts`: on "Printing problem" without an order number the guest is asked "continue without receipt?"; Yes re-sends the same body with the same `OrderGuid` and `?skip=true` (once per attempt), No sends `abortRequest`. **Live 2026-10-16: the dev backend answers 409 "Printing problem" to every order and `IsSuccess: true` to the resend, both in ~1 s** (`docs/reference/api-samples/CreateKioskOrderWithPinPayment-live-2026-10-16.md`). Whether a resend after a real post-payment printer failure would charge twice is still the backend's answer. | `IMPLEMENTED` (client); de-duplication `BLOCKED_BACKEND` |
| B9 | **Order number in the success answer** | Live 2026-10-16: `?skip=true` answers `{"IsSuccess":true,"Data":null}` — no `Data.AdditionalData`, no `Data.IdOrder`, although the handover document names them. | The order number (and `IdOrder`) in `Data` on success, or confirmation that an order is created at all when `Data` is null. | The kiosk shows its own short reference (last 6 characters of `OrderGuid`) as the order number and reports the receipt as not printed (`order.noNumber` in the log). | `NOT_VERIFIED_ON_REAL_INFRA` (order creation unconfirmed) |
| B7 | **Payment / order status lookup** | None usable: `CheckKioskPayment?reference=` is dead in the old kiosk and its reference was never returned (`kiosk-payment-flow.md`, "Dead code"). | A GET keyed by `OrderGuid` (or `IdOrder`) answering: charged yes/no, order stored yes/no, order number. Needed for restart recovery (a kiosk that restarts while the POST was open) and the guest's "check payment status". | `TmkOrderPayment.status()` answers `unknown` unless the POST closed in this process → the controller shows the assistance screen; the record is kept. | `BLOCKED_BACKEND` |
| B8 | **`ResponseMessage` catalogue** | Only `Aborted` and `Printing problem` are documented. A declined card, an unreachable terminal or a terminal timeout come back as some other text. | The list of messages and, for each, whether it guarantees that nothing was charged. | Every undocumented message, HTTP error and network failure is treated as outcome UNKNOWN (record kept, status / assistance offered), never as "declined". | `BLOCKED_BACKEND` (declined / terminal-offline as distinct outcomes) |
| B5 | **Plain-http menu images** | The test menu (`my.tabletmenukaart.nl`) sends every image URL as `http://`; the dev API sends `https://`. | Images over https (already true for both hosts as of 2026-10-21). | Development uses the Vite `/img-proxy` route; the production build rewrites `http://` image URLs to `https://` (`proxiedImg`), so no proxy is needed on a venue's server. Images were missing on the test server before this (2026-10-21). | `IMPLEMENTED` |
| B6 | **Design metadata per venue** (popular / new badges, category subtitles, cross-sell links, "finish" strips, reward) | Not in `getfullresources`: `ProductsTags` is empty in both samples, `SuggestionsScreen` is always `null`, subcategories have colours but no icon. `IsPromotion` + `PromotionFrom/To` exist and are used. | If the backend ever carries these, map them in `tmkMapper.ts`. The interim per-venue design file was withdrawn on 2026-10-20 (Alex: the design is coded in the kiosk); until the backend has fields, API menus show: promos from the flag, icons from the category name, Popular from the device's order tally, and nothing else of this list. | `src/adapters/http/tmkRules.ts` | `BLOCKED_BACKEND` (badges, subtitles, cross-sells, strips, reward) |
| B10 | **Modifier picks in the order** | The old kiosk never sent them (`Variants: []`, `ModifierWizards` ignored). `CreateKioskOrderWithPinPayment` has `Variants` (shape unknown) and `UpsaleCollection` (`UpsaleStepOptionModel {ProductId, Name, Price}` + `Quantity`; only an empty collection has been accepted live so far). | Confirm that modifier picks sent as `UpsaleCollection` entries (the option's own `ProductId`) reach the POS / kitchen ticket, or document the intended shape of `Variants`. | `kiosk-web/src/adapters/http/tmkMapper.ts` maps `ModifierWizards` to option groups (2026-10-20); `tmkOrder.ts` sends every pick as an `UpsaleCollection` entry; `order.sent` in the staff log lists the ids sent. **2026-10-20 afternoon: the dev endpoint answers HTTP 500 `An error has occurred.` to every order, with or without options, including the body that went through in the morning** — nothing can be verified until that is explained. | `IMPLEMENTED` (client); acceptance of a non-empty collection and POS delivery `NOT_VERIFIED_ON_REAL_INFRA` |
| B11 | **Ordering statistics ("Popular")** | None: the menu carries no sales ranking, `getfullresources` has no "popular" flag beyond what a venue design file adds. | Optional: a per-venue ranking (product ids by orders over a window) the kiosk can read at boot, or a `Popular` flag on products. | The kiosk keeps a per-device tally of accepted orders in `localStorage` (`src/engine/popularity.ts`) and shows the top five; a backend ranking would replace it in `popularProducts()`. | `IMPLEMENTED` (device-local simulation) |
